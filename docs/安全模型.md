# AI-Root 安全模型

本文详述 AI-Root 的权限边界设计，以及数据目录 ACL 隔离曾出现的三个缺陷
（A / B / C）的成因链、验证方式与回归测试。

> 概览见 [README §安全模型](../README.md#安全模型)。本文是**设计参考与故障复盘**，
> 面向需要审查该边界或排障的读者。

---

## 1. 权限边界在哪

### 1.1 为什么 ACL 才是真正的边界

`token.txt` 由**客户端与服务端共读同一文件**：

- 服务端（SYSTEM）读它来校验请求；
- 客户端（安装用户）读它来组装请求。

因此**能写该文件者即可自授权** —— 写入自制令牌后再用同一令牌请求，服务端会认可。
换言之，令牌本身不是边界，**`%ProgramData%\AI-Root\` 目录的 ACL 才是**。

这决定了 `set_dir_acl()` 的安全性等价于整个中继的安全性。

### 1.2 期望形态

| 主体 | 权限 | 理由 |
|---|---|---|
| `NT AUTHORITY\SYSTEM` | `(OI)(CI)(F)` | 服务自身读写令牌与日志 |
| `BUILTIN\Administrators` | `(OI)(CI)(F)` | 管理员维护能力 |
| 安装用户 | `(OI)(CI)(R)` | 客户端只需读令牌；**不得有写权限** |

`(OI)(CI)` 传播标志由目录自身向下继承，故「SYSTEM 写的事件文件用户可读」不受影响。

---

## 2. 缺陷 A：`/grant:r` 不清除其它 SID 的 ACE

`icacls /grant:r` 的 `:r`（replace）**只替换指定 SID 的那一条 ACE**，不会移除其它 SID 的 ACE。

原实现使用 `/inheritance:e` + `/grant:r`。于是 `C:\ProgramData` 继承来的
`BUILTIN\Users:(I)(CI)(WD,AD,WEA,WA)` 被**原样保留** —— 任意本地用户对该目录仍有**写权限**。

**后果链**：用户可写目录 ⇒ 可覆写 `token.txt` ⇒ 非提权用户**自授权拿到 SYSTEM 命令执行**。

实测对照（父目录含可继承的 Users 写 ACE）：

| 实现 | 结果 |
|---|---|
| `/inheritance:e`（原） | `BUILTIN\Users:(I)(OI)(CI)(WD,AD)` **残留** ❌ |
| `/inheritance:r`（修复） | 仅 `SYSTEM:(OI)(CI)(F)` + 用户只读 ✅ |

---

## 3. 缺陷 B：`icacls` 的 SID 参数缺 `*` 前缀

`get_user_sid()` 返回裸 SID（`S-1-5-21-...`），原实现直接拼成 `{sid}:(OI)(CI)R`。

`icacls` 会把裸 SID 当**账户名**去解析，失败即报
「账户名与安全标识间无任何映射完成」，并**整条命令非零退出、一个 ACE 都不写**
（grant 参数是全有或全无）。

正确写法：SID 前加 `*` 标记为 SID 字面量 —— `*S-1-5-21-...:(OI)(CI)R`。

---

## 4. 为何两缺陷必须一起修

缺陷 B 原本被缺陷 A **掩盖** —— `/inheritance:e` 保留了继承来的 `SYSTEM:F`，
所以即使显式授权全部失败，服务照样有权限，故障不显现。

一旦单独把 A 修成 `/inheritance:r` 而不管 B：

1. 继承 ACE 已被清除；
2. 显式 ACE 又写入失败（缺 `*` 前缀）；
3. ⇒ **目录 DACL 变空，SYSTEM 自己都进不去，服务彻底锁死。**

**这是本项目最重要的一条教训：修一个「被掩盖的缺陷」时必须先确认掩盖它的机制是什么。**

---

## 5. 缺陷 C：服务启动把自己降级为只读

### 5.1 症状

服务安装并启动后，`%ProgramData%\AI-Root` 的 ACL 变成
`NT AUTHORITY\SYSTEM:(OI)(CI)(R)` —— SYSTEM 只剩**只读**。

于是以 LocalSystem 运行的服务**无法再写** `token.txt` / `events.jsonl` / `exec.log`，
整个中继不可用（看似「服务在跑」实则已废）。

### 5.2 根因链

1. `run_pipe_server()` 在服务启动时调用 `common::set_dir_acl(&data_dir())` 固化目录 ACL；
2. 此时进程身份是 **LocalSystem**，而旧实现内部用 `get_user_sid()` 取「当前用户」；
3. `get_user_sid()` 跑 `whoami /user` → 以 SYSTEM 身份返回 **`S-1-5-18`**（SYSTEM 自己），
   而**不是**安装用户；
4. 于是「授予当前用户只读」那步实际执行成 `grant_one("*S-1-5-18:(OI)(CI)R")`；
5. 而 `:r` 是 **replace** 语义 → **覆盖掉刚授予的 `SYSTEM:(F)`**；
6. 结果服务每次启动都自降为只读。

### 5.3 为何兜底没拦住（顺序性缺陷）

`acl_has_system_full()` 自检确实检测到了缺失并补写，但补写用的 ACE 是
`*S-1-5-18:(OI)(CI)F`，而**同一次调用里后面紧跟的用户授权又把它 replace 回 `(R)`**
（`grant_one` 逐条独立调用，顺序即「先 F 后 R」，后者覆盖前者）。

属**顺序性缺陷**，非「兜底失效」。

### 5.4 实测证据

真机复现：停服务 → 手工 `icacls ... /grant:r "*S-1-5-18:(OI)(CI)F"`（SYSTEM 恢复 `(F)`）
→ 启动服务 → ACL **立即退回** `SYSTEM:(R)`。反复稳定复现。

### 5.5 修复

把「选谁作为待授权用户」抽成**纯函数** `select_grant_sid(persisted, current)`：

1. 优先读持久化的 `sid.txt`（install 阶段以管理员身份写入，是**权威**来源）；
2. 回退到当前进程身份，但**硬性拒绝** `S-1-5-18`；
3. 两者皆 SYSTEM 或皆不可用 → `None`，走 Interactive 只读退化分支（而非降级 SYSTEM）。

`granted_user_sid()` 负责取值（读文件 + `whoami`）后委托该纯函数；
`set_dir_acl` 改用 `granted_user_sid()`。

---

## 6. 修复后的完整实现要点

`common.rs::set_dir_acl`：

1. 先 `/inheritance:r` 断开继承并清除全部继承 ACE；
2. 显式授予 `SYSTEM:(OI)(CI)F`、`Administrators:(OI)(CI)F`、`当前用户:(OI)(CI)R`；
3. SID 一律加 `*` 前缀标记为 SID 字面量；
4. **逐条独立** `grant_one()` 调用（不再把三条 grant 塞进一条命令），单条失败不牵连其它；
5. 收尾自检 `acl_has_system_full()`，若 SYSTEM 完全控制 ACE 缺失则立即补写
   —— 从结构上消除「空 DACL 锁死」这一失败模式。

> 注意 `acl_has_system_full()` 是**兜底**而非主防线 —— 它会被同调用内后续的 grant 覆盖，
> 故缺陷 C 的修复落在 `granted_user_sid()` 的选值逻辑上。

### 真机修复后 ACL（服务重启后仍保持）

| 主体 | 权限 |
|---|---|
| `<机器名>\<用户名>`（安装用户） | `(OI)(CI)(R)` |
| `BUILTIN\Administrators` | `(OI)(CI)(F)` |
| `NT AUTHORITY\SYSTEM` | `(OI)(CI)(F)` ✅ |

端到端验证：非提权 `AI-Root run "whoami /user"` → `nt authority\system S-1-5-18`；
`AI-Root run "cmd /c echo ... > %ProgramData%\AI-Root\probe.txt"` → `exit=0` 且文件落盘成功。

---

## 7. Windows 行为易误判点

以管理员 `install` 时目录 owner 是当前用户。`icacls` 改 DACL 后，
Windows **会自动把 owner 原经继承（`ProgramData` → `BUILTIN\Administrators:(F)`）
获得的完全控制固化为显式 `(F)` ACE**。

故真实 ACL 里必然多一条 `BUILTIN\Administrators:(F)` ——
这是 **Windows 的行为，不是 `set_dir_acl` 的输出**。

---

## 8. icacls 使用要点（实测）

| 要点 | 说明 |
|---|---|
| `MSYS_NO_PATHCONV=1` | Git Bash 下 `/grant` 会被 MSYS 当路径转换，必须先导出该变量 |
| **SID 必须带 `*`** | 否则被当账户名解析失败（缺陷 B）；账户名则不需要 `*` |
| 显示的是**账户名** | 非 SID。且 `whoami` 返回**小写**而 `icacls` 打印**大写** → 比较须 `.to_lowercase()` 归一化 |
| **grant 全有或全无** | 一条坏参数会让同一命令内其它正当 ACE 一起丢失 → **逐条独立**调用 |

## 9. 回归测试与变异验证

### 9.1 测试清单

| 测试 | 覆盖 |
|---|---|
| `set_dir_acl_strips_inherited_users_write` | 缺陷 A：构造「父目录授予可继承 Users 写权限」前提 → 断言写权限被剥离、SYSTEM 保留完全控制、当前用户保留只读。**前提不成立时测试主动失败**（避免「前提没了还假装通过」） |
| `set_dir_acl_is_idempotent` | 重复调用结果稳定 |
| `set_dir_acl_never_downgrades_system` | 缺陷 C：① 纯逻辑组 6 条断言覆盖 `select_grant_sid` 的 persisted/current 全组合（含两者皆 SYSTEM、`sid.txt` 被污染、非法值、空白裁剪）；② 集成组人为把 scratch 目录 SYSTEM 降为 `(R)` 并断言前提成立，调**真实** `set_dir_acl`，断言 SYSTEM 重新获得 `(F)` |

### 9.2 变异验证记录

**验证测试有效性的唯一方法是变异测试** —— 改坏实现，看测试是否 FAILED。

| 注入的变异 | 结果 |
|---|---|
| 还原缺陷 A（`/inheritance:r` → `/inheritance:e`） | 两个 ACL 测试均 FAILED ✅ |
| 还原缺陷 B（去掉 SID 的 `*` 前缀） | 首次**未被捕获** ❌ → 据此补了「当前用户保留只读 ACE」断言后才捕获 |
| 缺陷 C 首版：断言 `granted_user_sid() != S-1-5-18` | **实测漏检** ❌ —— 因测试进程本来就不是 SYSTEM，`whoami` 返回真实用户。抽出纯函数 `select_grant_sid()` 后可注入 `(SYSTEM, SYSTEM)` 组合断言 `None` |
| 移除 `current` 分支的 `sid != LOCAL_SYSTEM_SID` 守卫 | FAILED ✅ |
| 移除 `persisted` 分支的同一守卫 | FAILED ✅ |

> **教训**：无法在测试环境复现的前提（此处是「进程身份 = SYSTEM」），
> **要么抽成纯函数，要么就不算被测到**。不跑一次变异，就不知道断言其实没覆盖到。

## 10. v1.1 补充：ACL 之外的授权层（2026-10-21）

历史缺陷 A/B/C 修的是「**谁能读令牌**」。但即使 ACL 完美，v1.0 仍有另一个
结构性问题：**令牌本身就是一张全权凭据** —— 读到它就能让 LocalSystem 执行
任意命令。这不是 ACL 能解决的，属于授权模型缺失。

v1.1 增加了第二层边界，完整说明见 [授权策略.md](授权策略.md)。本节只记录
与 ACL 直接相关的三处改动。

### 10.1 `set_dir_acl` 从 fail-open 改为 fail-closed

原实现返回 `()`，三处 `Command::new("icacls").output()` 的结果全部 `let _ =` 丢弃。
后果：`/inheritance:r` 成功而后续 grant 全失败时，目录可能落入
「SYSTEM 无写权限」或「继承已断但显式 ACE 缺失」，而调用方认为成功并继续。

现在：每条 `icacls` 都检查 `status.success()`，任一步失败返回 `Err(AclError)`；
调用方（`ensure_token` / `set_enabled` / `rotate_token` / `run_pipe_server`）
全部传播；服务启动时失败 → **不进入主循环**（SCM 记启动失败），并写
`acl_setup_failed` 事件。

### 10.2 自检判据从「文本 contains」改为「二进制 DACL」

原 `acl_has_system_full()` 唯一判据是 `line.contains("SYSTEM") && line.contains("(F)")`。
它覆盖不到：

- `BUILTIN\Users:(OI)(CI)(F)` 残留（含 SYSTEM 行的同时用户仍可写）；
- 继承未断（`(I)` 标记仍在）；
- `Everyone` / `Authenticated Users` / `INTERACTIVE` 的写 ACE；
- 非英文 Windows 上 `SYSTEM` 显示名不同 → 误判为缺失并重复补写 ACE。

新 `verify_dir_acl()` 用 `GetNamedSecurityInfoW` + `GetAclInformation` + `GetAce`
遍历真实 DACL，用 **SID** 而不是账户名判断：

| 校验项 | 判据 |
|---|---|
| DACL 非空 | `ppDacl != NULL`（NULL DACL = 所有人完全控制） |
| 危险主体无写权限 | `S-1-1-0`(Everyone) / `S-1-5-32-545`(Users) / `S-1-5-11`(Authenticated Users) / `S-1-5-4`(INTERACTIVE) / `S-1-5-7`(ANONYMOUS) / `S-1-5-32-546`(Guests) / `S-1-5-2`(NETWORK) 的允许 ACE 中不得出现写类掩码 |
| SYSTEM 有写权限 | `S-1-5-18` 的允许 ACE 含写类掩码 |
| 无残留继承 ACE | `AceFlags & INHERITED_ACE(0x10) == 0` |

写类掩码 = `FILE_WRITE_DATA | FILE_APPEND_DATA | FILE_WRITE_EA | FILE_WRITE_ATTRIBUTES
| DELETE | WRITE_DAC | WRITE_OWNER | GENERIC_ALL | GENERIC_WRITE`。

任何一条不满足 → `Err`，附带**具体是哪个主体、哪个掩码**（便于排障，而不是只说「失败」）。

### 10.3 令牌写入顺序

原 `ensure_token` 是「写 token.txt → set_dir_acl」。中间存在一个窗口：
令牌已经在弱权限目录里，可被任意本地用户读取。

现在改为「set_dir_acl → 写 token.txt」。并且令牌**已存在**时也会
`verify_dir_acl` 复验（原实现直接 `return`，导致 ACL 被改坏后永不修复）。

### 10.4 回归测试

| 测试 | 覆盖 |
|---|---|
| `verify_dir_acl_accepts_hardened_dir` | 正确配置必须通过（防「一律报错」） |
| `verify_dir_acl_rejects_everyone_write` | 人为授予 `Everyone:(OI)(CI)W` → 必须检出并指出主体 |
| `verify_dir_acl_detects_inherited_aces` | 父目录授予可继承的 Users 写 → 子目录必须检出继承 ACE |
| `set_dir_acl_errors_on_missing_dir` | 目录不存在必须返回 `Err`（而非静默「成功」） |
| `ensure_token_refuses_when_dir_is_writable_by_everyone` | 令牌已存在但目录可被 Everyone 写 → 拒绝 |
| `set_dir_acl_strips_inherited_users_write` / `set_dir_acl_is_idempotent` / `set_dir_acl_never_downgrades_system` | 原有的 A/B/C 回归，保持全绿 |

> ⚠ 未验证项：以上测试在**测试进程（管理员身份）**下运行。
> 「服务以 LocalSystem 启动时」的路径（`granted_user_sid()` 从 `sid.txt` 取安装用户）
> 需在可恢复的 Windows 虚拟机上安装服务后验证 —— 本机未安装服务，因此这部分**未实测**。
