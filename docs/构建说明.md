# AI-Root 构建说明

本文记录构建系统的设计取舍，以及几个**只在特定环境下才暴露**的坑的根因分析。

> 快速上手见 [README §构建](../README.md#构建)。本文面向需要修改构建脚本或排障的读者。

---

## 1. 设计：配置与脚本职责分离

- **`.cargo/config.toml`** —— 承载所有**与机器无关**的稳定配置（`target-dir` 等）。单一事实来源。
- **`build.sh` / `build.ps1`** —— 只做**与机器相关**的事：定位工具链、注入 binutils、调 cargo。

两者共享 `.cargo/config.toml`，不再各自维护一份会漂移的重复逻辑。

> 该重构的直接动因是一个真实缺陷：`build.ps1` 曾漏导出 `CARGO_HOME`，
> 导致两个脚本使用不同的 crate registry 源，产物字节不一致。

---

## 2. 设计原则：向系统自省，而非猜测路径

| 信息 | 获取方式 | 可移植性 |
|---|---|---|
| rust 根 | `rustup show home` 反推（**并校验 toolchain 真实存在**） | 高——只要 rustup 在 PATH |
| cargo | `rustup which cargo` 直接定位（绕开 rustup shim） | 高 |
| binutils | `MINGW_BINUTILS_BIN` → PATH 中的 `as.exe` → 常见 MSYS2/MinGW 位置 | 中——gnu 需用户提供 |

所有候选路径都经过**存在性校验**后才采用。

### 陷阱 1：`rustup show home` 只回显环境变量

它**不验证目录是否存在**。新装/迁移后会话常残留陈旧值（指向已删目录），
直接采信会得到「工具链不存在」的假结论。故**所有候选都必须校验后才采用**。

### 陷阱 2：`TARGET`（目标三元组）≠ `TOOLCHAIN`（工具链名）

工具链目录形如 `stable-x86_64-pc-windows-gnu`，比 target 多 `stable-` 前缀。
混用会导致误判。

---

## 3. host toolchain 名 ≠ 目标三元组（CI 上验证）

```bash
rustup toolchain install stable --target x86_64-pc-windows-gnu
```

上面这条命令装出来的是 **`stable-x86_64-pc-windows-msvc`**（host 不变），
只是**附加**了 gnu target。

因此 `toolchains/` 下**没有** `stable-x86_64-pc-windows-gnu` 目录，
却能正常执行 `cargo build --target x86_64-pc-windows-gnu`（cross-compile）。

**结论**：不能按目录名硬匹配，要按「**是否已装该 target**」挑选工具链。

---

## 4. 不要假设 rust 根目录结构

rustup 有两种常见布局：

| 布局 | 形态 |
|---|---|
| 自定义 | `<root>\{cargo, rustup}` |
| 默认（官方安装器） | `%USERPROFILE%\{.cargo, .rustup}` |

二者的**唯一共同点**是「cargo 与 rustup 是平级目录」，但**绝不是 `cargo/` 与 `rustup/` 这样的固定名**。

旧实现把 `<root>/cargo` 与 `<root>/rustup` 当固定结构写死 →
在 CI 上 `dirname($RUSTUP_HOME)` 下根本没有 `cargo\` 子目录，所有候选全部落空。

> **为什么本机测不出**：本机恰好是自定义布局，**永远命中第一个候选**。
> 这类「恰好匹配当前环境的假设」在单一环境上开发时，无论是人还是本地测试都发现不了。

**正确做法**：直接问 rustup 要路径 ——

```bash
rustup which cargo   # 返回当前活动 toolchain 的真实 cargo.exe 绝对路径
```

因此它不依赖具体布局，也不依赖 host 名。

## 5. gnu 目标的资源嵌入：`embed-resource` 的 host/target 陷阱

`embed-resource` 2.x 通过 `#[cfg(target_env = "msvc")]` 选择模块，而该 cfg 指的是
**编译 build script 的 host**，**不是** cargo `--target` 指定的目标。

因此在「**msvc host + gnu target**」的 cross-compile 场景下：

1. 它编译的是 `windows_msvc` 分支；
2. 调用 `rc.exe` 产出 **MSVC 格式 `.lib`**；
3. gnu 链接器报 `file format not recognized: file format not recognized`。

> 该 crate 的 `windows_msvc.rs` 甚至用 `HOST` 环境变量取架构 ——
> 进一步印证它的设计前提是「host == target」。**host ≠ target 时必然出错。**

**修复**：**移除该依赖**。`build.rs` 的 gnu 分支改为直接调用 `windres`：

```bash
windres --include-dir <out> -I assets <rc> -O coff <out.o>
```

产出 **COFF 目标文件**交链接器直接消费，绕过 host 探测。验证方式：检查 PE `.rsrc` 段
（实测 size 8712）。

## 6. 仓库路径必须纯 ASCII

MinGW 的 `ld`/`dlltool` 按 **ANSI 代码页（GBK）** 解释路径参数。

当**产物落进中文路径**时：

```
ld.exe: cannot find <中文路径>\target\release\deps\libsyn-xxx.rlib
No such file or directory
```

注意错误里的中文**显示正常**，但 `ld` 实际按 GBK 解读 UTF-8 字节，故找不到真实文件。

**最先炸的是 proc-macro 依赖**（`serde_derive` 等）—— 因其必须先编成 `.dylib` 供 host 加载，
这一步走 `ld`。

### 精确边界（反直觉）

**只有「产物路径」必须 ASCII，「源码路径」其实无所谓**：

| 仓库路径 | 产物路径 | 结果 |
|---|---|---|
| 中文 | 中文 | 失败 |
| 中文 | 外部纯 ASCII `CARGO_TARGET_DIR` | 成功（曾用此法绕过） |
| ASCII | 仓库内 `target/` | 成功（**当前做法**） |

### 教训

**不要用脚本对抗路径问题，要让路径不再有问题。**

迁移到 ASCII 路径后，外部 `CARGO_TARGET_DIR`、ASCII 前置校验等一整套绕行机制**全部删除**，
脚本随之瘦身。

## 7. gnu 链接需要完整 binutils

rustup 的 `self-contained` 目录实测只有 `dlltool.exe` / `ld.exe` / `x86_64-w64-mingw32-gcc.exe`，
**缺 `as.exe`**，不能单独完成链接。

两个脚本按以下顺序**自动探测**：

1. `MINGW_BINUTILS_BIN`（环境变量）
2. `PATH` 中已有的 `as.exe`
3. 常见 MSYS2 / MinGW 安装位置

安装方式见脚本报错提示（MSYS2 或镜像源）。

### Git Bash 的 PATH 只认 POSIX 形式

把 `D:/...` 或 `D:\...` 写进 `PATH` 后，`command -v dlltool.exe` / `which` 一律查不到
（**不是 Permission denied，是彻底找不到**），导致 cargo 回落到 `CARGO_HOME\bin` 的 rustup shim，
最终报：

```
error calling dlltool 'dlltool.exe': program not found
```

`build.sh` 用 `to_posix()` 统一转换，并直连 toolchain 内的真实 `cargo.exe`；
`build.ps1` 为原生 Windows 路径语义，无此问题。

### `CARGO_HOME\bin` 下的 cargo/rustc 是 rustup shim

它们与 `rustup.exe` 是硬链接（MD5 相同），**不要直接用**。

## 8. 二进制可复现性：结论（不要再追）

**结论：本项目不保证逐字节可复现，且不应以此作为构建正确性标准。**

实测事实：

- 同一台机器、同一源码，**同一脚本连续两次构建，字节也不一致**。
  （此前认为「各脚本可复现」是 cargo fingerprint 缓存造成的假象。）
- **根因在上游**：GNU `dlltool` 默认把**时间戳**写进 `kernel32_dll_imports_lib`，
  该 lib 的内容哈希又被编进最终产物（PE 内可见 `_head_D_..._kernel32_dll_imports_lib`），
  进而改变符号表布局 → 约 **3.75%** 的字节差异。`PE TimeDateStamp` / `Checksum` 本身也不可复现。
- 已验证 `dlltool --deterministic-libraries` + 固定输出路径 → md5 完全一致。
  **但 rustc 内部直接 spawn `dlltool`，无法经 `RUSTFLAGS` 注入该参数**；
  bash 写的 `dlltool.exe` shim 也无效（rustc 走 Windows `CreateProcess`，不执行 bash 脚本）。
  → **当前不可行。**

### 判定标准

以「**测试通过 + 源码级一致**」为准，**不要以二进制字节相等作为构建正确性标准**。

若确需可复现构建，须改用 **msvc** 工具链（`link.exe` 无此问题）。

## 9. `profile.release` 的 `strip` 选择

| 配置 | 体积 | 符号数 | panic 回溯 |
|---|---|---|---|
| `symbols` | 842 KB | 0 | **空**，仅一行 `note: Some details are omitted` |
| **`debuginfo`（当前）** | **1.07 MB** | **3333** | 完整函数名 + 调用链 |
| `none` | 3.41 MB | 完整 | 多出体积几乎全是无用 debug 段 |

**为什么不用 `symbols`**：本项目以 LocalSystem 执行任意命令，线上崩溃时若拿不到任何符号，
排障代价远高于 256 KB 的体积收益。

**补充**：panic 的 `file:line:col` 位置信息编在 panic **元数据**中，
**两种配置下都有**，不受 `strip` 影响。

## 10. CI 配置

`.github/workflows/ci.yml`，`windows-latest`，**双 job**：

| job | toolchain | 内容 |
|---|---|---|
| `build-msvc` | `x86_64-pc-windows-msvc` | `build.ps1` 构建 → `cargo test` → 打包上传 `AI-Root-windows-x64` 工件 |
| `build-gnu` | `x86_64-pc-windows-gnu` | 经 `msys2/setup-msys2` 装完整 binutils → `bash build.sh` → `cargo test` |

### 为什么必须有两个 job

本机开发环境是 **gnu-only**，msvc job 不可能覆盖 gnu 路径。

`build.sh` 曾长期因 binutils / PATH 问题无法构建，**但 CI 一直是绿的** ——
因为当时只验了 msvc。`build-gnu` 专门堵住这个盲区：它走的是**开发者实际使用的 `build.sh`**，
而非另写一套等价逻辑，确保 CI 验的就是本机跑的。

### CI 陷阱：顶层 `env:` 不能用 `${{ runner.* }}`

```yaml
env:                    # ← 顶层 env
  CARGO_TARGET_DIR: ${{ runner.temp }}\target   # ← 致命
```

`runner.temp` 依赖 runner 实例，而顶层 `env:` 在**解析期**展开（此时 runner 尚不存在）
→ GitHub 拒绝**整份文件**。

job 级 `env:` 同样不可用；**只有 step 级 `env:` 与 `run:` 脚本内可用**。

**误导性症状指纹**（记牢，省很多时间）：

| 症状 | 含义 |
|---|---|
| 工作流名显示为**文件路径**（如 `.github/workflows/ci.yml`）而非 `name:` 值 | 解析失败，`name` 读不到 |
| `check_runs: 0`、jobs 列表为空、日志下载 404 | 从未实例化 job |
| push 后**数秒内**即 failure | 解析期就挂了，根本没跑构建 |
| `workflow_dispatch` 返回 **422**「没有该 trigger」 | 整份文件没解析成功，trigger 也不认 |

**最快的根因入口**：
`POST /repos/{owner}/{repo}/actions/workflows/{id}/dispatches` 返回的 **422 body**
会直接给出 GitHub 解析器的**行号/列号与具体原因**。

### 不要手工下载 `.pkg.tar.zst`

该格式是 zstd 压缩，实测本机 GNU tar 1.35、Python 标准库（无 `zstandard`）均无法解压，
runner 上是否可行**无法在本地验证** —— 属于「靠猜」。改用 `msys2/setup-msys2` 由官方 action 保证正确性。
