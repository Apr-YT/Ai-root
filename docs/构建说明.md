# AI-Root 构建说明

构建脚本的设计取舍，以及几个只在特定环境才暴露的问题的成因。
快速上手见 [README §构建](../README.md#构建)。

---

## 1. 配置与脚本的职责划分

- `.cargo/config.toml`：与机器无关的稳定配置，例如 `target-dir`。单一事实来源。
- `build.sh` / `build.ps1`：与机器相关的事，定位工具链、注入 binutils、调 cargo。

两个脚本共用 `.cargo/config.toml`，不各自维护一份会漂移的重复逻辑。

这样划分的直接原因是一个真实缺陷：`build.ps1` 曾经漏导出 `CARGO_HOME`，
导致两个脚本使用不同的 crate registry，产物字节不一致。

---

## 2. 工具链定位

| 信息 | 获取方式 | 可移植性 |
|---|---|---|
| rust 根 | `rustup show home` 反推，并校验 toolchain 真实存在 | 高，只要 rustup 在 PATH |
| cargo | `rustup which cargo`，绕开 rustup shim | 高 |
| binutils | `MINGW_BINUTILS_BIN`，其次 PATH 中的 `as.exe`，再次常见 MSYS2/MinGW 位置 | 中，gnu 需要用户提供 |

所有候选路径都要先确认存在再采用。

### `rustup show home` 不验证目录是否存在

它只回显环境变量。新装或迁移之后，会话里常残留指向已删目录的陈旧值，
直接采信会得出「工具链不存在」的错误结论。

### `TARGET` 与 `TOOLCHAIN` 不是一回事

工具链目录形如 `stable-x86_64-pc-windows-gnu`，比 target 多一个 `stable-` 前缀。
把两者混用会误判。

## 3. host 工具链名与目标三元组

```bash
rustup toolchain install stable --target x86_64-pc-windows-gnu
```

这条命令装出来的是 `stable-x86_64-pc-windows-msvc`，host 不变，
只是附加了 gnu target。

因此 `toolchains/` 下没有 `stable-x86_64-pc-windows-gnu` 这个目录，
但 `cargo build --target x86_64-pc-windows-gnu` 仍然可用，走的是 cross-compile。

所以不能按目录名硬匹配，要按「是否已安装该 target」来挑工具链。

---

## 4. rust 根目录没有固定结构

rustup 有两种常见布局：

| 布局 | 形态 |
|---|---|
| 自定义 | `<root>\{cargo, rustup}` |
| 官方安装器默认 | `%USERPROFILE%\{.cargo, .rustup}` |

这两者的唯一共同点是「cargo 与 rustup 是平级目录」，目录名并不固定为
`cargo/` 和 `rustup/`。

早期实现把 `<root>/cargo` 与 `<root>/rustup` 当固定结构写死，于是在 CI 上
`dirname($RUSTUP_HOME)` 下面根本没有 `cargo\` 子目录，所有候选全部落空。

本机测不出这个问题，因为本机恰好是自定义布局，永远命中第一个候选。
这类「恰好匹配当前环境」的假设，在单一环境上开发时，人和本地测试都发现不了。

正确做法是直接问 rustup 要路径：

```bash
rustup which cargo   # 返回当前活动 toolchain 的真实 cargo.exe 绝对路径
```

这样既不依赖布局，也不依赖 host 名。

## 5. gnu 目标的资源嵌入

`embed-resource` 2.x 通过 `#[cfg(target_env = "msvc")]` 选择模块，而这个 cfg 判断的是
编译 build script 的 host，不是 cargo `--target` 指定的目标。

所以在「msvc host + gnu target」的交叉编译场景下：

1. 它编译的是 `windows_msvc` 分支；
2. 调用 `rc.exe` 产出 MSVC 格式的 `.lib`；
3. gnu 链接器报 `file format not recognized`。

该 crate 的 `windows_msvc.rs` 里还用 `HOST` 环境变量取架构，可见它的设计前提是
host 等于 target。两者不等时必然出错。

修复方式是移除这个依赖，`build.rs` 的 gnu 分支改为直接调用 `windres`：

```bash
windres --include-dir <out> -I assets <rc> -O coff <out.o>
```

产出的 COFF 目标文件交给链接器直接消费，绕过 host 探测。
验证方式是检查 PE 的 `.rsrc` 段，实测 size 8712。

## 6. 仓库路径必须是 ASCII

MinGW 的 `ld` 和 `dlltool` 按 ANSI 代码页（GBK）解释路径参数。

产物落进中文路径时：

```
ld.exe: cannot find <中文路径>\target\release\deps\libsyn-xxx.rlib
No such file or directory
```

错误信息里的中文显示正常，但 `ld` 实际是按 GBK 解读 UTF-8 字节，所以找不到真实文件。

最先出错的是 proc-macro 依赖（`serde_derive` 等），因为它们必须先编成 `.dylib`
供 host 加载，这一步走 `ld`。

### 只有产物路径需要是 ASCII

源码路径其实无所谓：

| 仓库路径 | 产物路径 | 结果 |
|---|---|---|
| 中文 | 中文 | 失败 |
| 中文 | 外部纯 ASCII `CARGO_TARGET_DIR` | 成功 |
| ASCII | 仓库内 `target/` | 成功，当前做法 |

不要用脚本对抗路径问题，要让路径本身不再有问题。仓库迁到 ASCII 路径之后，
外部 `CARGO_TARGET_DIR`、ASCII 前置校验这一整套绕行机制全部删除，脚本随之简化。

## 7. gnu 链接需要完整 binutils

rustup 的 `self-contained` 目录实测只有 `dlltool.exe`、`ld.exe`、
`x86_64-w64-mingw32-gcc.exe`，缺 `as.exe`，不能单独完成链接。

两个脚本按以下顺序自动探测：

1. `MINGW_BINUTILS_BIN` 环境变量
2. `PATH` 中已有的 `as.exe`
3. 常见 MSYS2 / MinGW 安装位置

安装方式见脚本报错提示（MSYS2 或镜像源）。

### Git Bash 的 PATH 只认 POSIX 形式

把 `D:/...` 或 `D:\...` 写进 `PATH` 之后，`command -v dlltool.exe` 和 `which`
一律查不到，不是权限被拒，是彻底找不到。于是 cargo 回落到 `CARGO_HOME\bin`
的 rustup shim，最终报：

```
error calling dlltool 'dlltool.exe': program not found
```

`build.sh` 用 `to_posix()` 统一转换，并直连 toolchain 内的真实 `cargo.exe`。
`build.ps1` 用原生 Windows 路径语义，没有这个问题。

### `CARGO_HOME\bin` 下的 cargo 与 rustc 是 rustup shim

它们和 `rustup.exe` 是硬链接（MD5 相同），不要直接使用。

## 8. 可复现性

本项目不保证逐字节可复现，也不应该拿字节相等当构建正确性的标准。

实测情况：

- 同一台机器、同一份源码，用同一个脚本连续构建两次，字节也不一致。
  此前认为「各脚本可复现」，那是 cargo fingerprint 缓存造成的假象。
- 根因在上游。GNU `dlltool` 默认把时间戳写进 `kernel32_dll_imports_lib`，
  这个 lib 的内容哈希又会被编进最终产物（PE 里能看到
  `_head_D_..._kernel32_dll_imports_lib`），进而改变符号表布局，
  造成约 3.75% 的字节差异。`PE TimeDateStamp` 和 `Checksum` 本身也不可复现。
- `dlltool --deterministic-libraries` 加固定输出路径已验证能让 md5 完全一致。
  但 rustc 内部直接 spawn `dlltool`，无法通过 `RUSTFLAGS` 注入这个参数；
  用 bash 写 `dlltool.exe` shim 也无效，因为 rustc 走 Windows `CreateProcess`，
  不执行 bash 脚本。当前不可行。

判定标准用「测试通过 + 源码级一致」，不要用二进制字节相等。
确实需要可复现构建时，改用 msvc 工具链，`link.exe` 没有这个问题。

## 9. `profile.release` 的 strip 选择

| 配置 | 体积 | 符号数 | panic 回溯 |
|---|---|---|---|
| `symbols` | 842 KB | 0 | 空，只有一行 `note: Some details are omitted` |
| `debuginfo`（当前） | 1.07 MB | 3333 | 完整函数名和调用链 |
| `none` | 3.41 MB | 完整 | 多出来的体积几乎全是无用 debug 段 |

不用 `symbols` 的原因：本项目以 LocalSystem 执行命令，线上崩溃时如果拿不到任何符号，
排障代价远高于省下的 256 KB。

panic 的 `file:line:col` 位置信息编在 panic 元数据里，两种配置下都有，不受 strip 影响。

## 10. CI 配置

`.github/workflows/ci.yml` 跑在 `windows-latest`，两个 job：

| job | toolchain | 内容 |
|---|---|---|
| `build-msvc` | `x86_64-pc-windows-msvc` | `build.ps1` 构建，`cargo test`，打包上传 `AI-Root-windows-x64` |
| `build-gnu` | `x86_64-pc-windows-gnu` | 经 `msys2/setup-msys2` 装完整 binutils，`bash build.sh`，`cargo test` |

两个 job 都需要。开发者本机是 gnu-only，msvc job 覆盖不到 gnu 路径。

`build.sh` 曾长期因为 binutils 和 PATH 问题无法构建，而 CI 一直是绿的，
因为当时只验了 msvc。`build-gnu` 专门堵这个盲区，它走的是开发者实际在用的
`build.sh`，不是另写一套等价逻辑。

### 顶层 `env:` 不能用 `${{ runner.* }}`

```yaml
env:                    # ← 顶层 env
  CARGO_TARGET_DIR: ${{ runner.temp }}\target   # ← 致命
```

`runner.temp` 依赖 runner 实例，而顶层 `env:` 在解析期就展开，此时 runner 还不存在。
结果是 GitHub 拒绝整份文件。job 级 `env:` 同样不可用，只有 step 级 `env:`
和 `run:` 脚本内可以用。

解析失败时的症状比较误导，认这几条能省不少时间：

| 症状 | 含义 |
|---|---|
| 工作流名显示为文件路径（如 `.github/workflows/ci.yml`）而不是 `name:` 的值 | 解析失败，读不到 name |
| `check_runs: 0`，jobs 列表为空，日志下载 404 | job 从未实例化 |
| push 后几秒内就 failure | 解析期挂了，根本没跑构建 |
| `workflow_dispatch` 返回 422「没有该 trigger」 | 整份文件没解析成功，trigger 也不认 |

最快的根因入口是
`POST /repos/{owner}/{repo}/actions/workflows/{id}/dispatches` 返回的 422 body，
里面会直接给出 GitHub 解析器的行号、列号和具体原因。

### 不要手工下载 `.pkg.tar.zst`

该格式是 zstd 压缩，实测本机的 GNU tar 1.35 和 Python 标准库（没有 `zstandard`）
都无法解压，runner 上是否可行也无法在本地验证，属于靠猜。
改用 `msys2/setup-msys2`，由官方 action 保证正确。
