# AI-Root 授权策略与确认机制

授权模型与确认机制。持有令牌只表示可以发起请求，每个请求还要按下面的顺序判定。

- 审计发现的原始问题与修复方案见 [audit/SECURITY_REFACTOR_AUDIT.md](audit/SECURITY_REFACTOR_AUDIT.md)
- ACL 边界的设计依据见 [安全模型.md](安全模型.md)

---

## 1. 三层判定

每个请求按下面的固定顺序判定，顺序不能调换：

```text
1. 内置保护（硬编码）        → Deny      策略文件无法覆盖
2. 策略文件里的 deny 规则     → Deny      全部先扫，保证「禁止优先」
3. approved_services 名单    → Allow     动态放行指定服务重启
4. 策略文件里的 allow 规则    → Allow     严格匹配
5. 策略文件里的 confirm 规则  → Confirm   进入确认流程
6. 未匹配                    → default_decision（默认 confirm）
```

三种结果：

| 结果 | 含义 | 能否被绕过 |
|---|---|---|
| `Allow` | 严格匹配的低风险操作，直接执行 | 不适用 |
| `Confirm` | 需要人工确认，无确认通道时等同拒绝 | 只能由管理员 `approve` |
| `Deny` | 明确禁止 | 任何确认都不放行 |

内置保护优先于一切策略。即使你在 `policy.toml` 里写一条放行 `cmd` 的 allow 规则，
`cmd` 仍然会被内置的 `builtin:shell-host` 拒绝。这是代码里的结构性保证，不是配置项。

## 2. 两种执行形态

| 形态 | 命令 | 是否经 shell | 策略能否精确匹配 |
|---|---|---|---|
| 结构化 argv | `AI-Root exec <程序> [参数...]` | 否，`CreateProcess` 直调 | 能，按程序、参数前缀、目录匹配 |
| 传统 shell | `AI-Root run "<命令>"` | 是，走 `cmd /C` | 不能，只能整条确认 |

优先用 `exec`。`run` 只留给必须依赖 cmd 语义（`for`、`|`、`dir`）的排障场景，
它默认进入人工确认。

### argv 的约束条件

- 程序被解析成绝对路径，只在 PATH 里查找，不查当前目录。这样客户端把 cwd 指向一个
  含 `git.exe` 的目录也劫持不了。
- 参数是数组，`&`、`|`、`>` 不会被当成 shell 语法解释。
- 审计日志里记的是真实的程序和参数，不是一层 `cmd /c` 外壳。

### 解释器等于代码执行

在 LocalSystem 下运行 `python`、`cargo`、`node` 这类解释器或编译器，效果上等于
允许任意代码执行，因为 `build.rs`、`npm postinstall`、`conftest.py` 都会被执行。

所以这套策略不追求禁止代码执行，边界放在三条上：

1. 不允许间接执行，包括 `cmd /c`、`powershell -enc`、`mshta`、`rundll32` 等，
   保证每次执行都能落到结构化审计里；
2. 不允许不可逆破坏，包括格式化、删卷、改引导、清审计、建管理员账户、装服务；
3. 不允许改动 AI-Root 自身，包括服务二进制、令牌、策略和服务配置。

如果你需要更严格的边界，把 `mode` 改为 `balanced` 并填 `workspace_roots`，
argv 执行就会被限制在指定目录内。

## 3. 配置文件

策略文件是 `%ProgramData%\AI-Root\policy.toml`，ACL 为 `SYSTEM:(F)`、`Administrators:(F)`、
安装用户 `(R)`，所以只有管理员能改，Agent 以安装用户身份运行只能读。

首次 `install` 时生成默认策略。查看当前生效值：

```powershell
AI-Root policy        # 规则数量、模式、自动允许范围
AI-Root config show   # 合并后的生效值，标注每项来自哪一层
```

### 3.1 字段

```toml
version = 2                  # 高于程序支持的版本会被拒绝
mode = "autonomy"            # autonomy | balanced | strict | disabled
default_decision = "confirm" # 未匹配时的归宿：allow | confirm | deny

workspace_roots = []         # balanced 模式下 argv 的 cwd 白名单（绝对路径）
approved_services = []       # 允许直接 restart_service 的服务名（大小写不敏感）
trusted_publishers = []      # update 信任根：发布者证书 SHA-256
allow_legacy_shell = false   # true 时 run 不再逐次确认
confirm_timeout_secs = 300   # 确认请求有效期，钳制到 30..3600

[[rule]]
id = "allow-git-status"      # 全局唯一，写入审计；重复会被拒绝
decision = "allow"           # allow | confirm | deny
op = "run_argv"              # 约束操作类型
program = "git"              # 程序 basename，大小写不敏感，可省 .exe
arg_prefix = ["status"]      # 参数前缀必须逐项相等，大小写敏感
note = "只允许查看状态"       # 给人看的说明，写进审计
```

规则可用的字段：

| 字段 | 作用 |
|---|---|
| `op` | `run_argv` / `run_shell` / `query_service` / `restart_service` / `query_system_info` / `read_state_file` |
| `program` | 程序 basename，大小写不敏感，可省略 `.exe` |
| `program_path` | 程序绝对路径，优先于 `program` |
| `arg_prefix` | 参数前缀逐项相等，大小写敏感 |
| `arg_forbid` | 参数中任意位置出现即不匹配 |
| `target` | op 的目标，精确匹配或 `前缀:*` |
| `cwd_roots` | 工作目录必须落在这些根内 |

填写的字段必须全部满足（AND 语义），不是任一命中。省略的字段表示不约束。

规则可以内联在 `policy.toml`，也可以拆到 `rules.d\*.toml`，后者更适合长期维护。

### 3.2 加载失败的处理

| 情况 | 行为 |
|---|---|
| 文件不存在，且没有 `state\policy.initialized` 标记 | 生成默认策略 |
| 文件不存在，但初始化标记还在 | 降级为只读，不重建默认策略 |
| TOML 解析失败、出现未知字段 | 降级为只读 |
| `version` 高于程序支持版本 | 降级为只读 |
| `version` 低于程序支持版本 | 按当前版本语义解释，字段是超集关系 |
| 规则 ID 重复、allow 规则过于宽泛、相对路径、指纹格式错 | 降级为只读 |
| 用户配置损坏 | 忽略用户层，管理员策略照常生效 |

降级是指进入 `locked_down`，只读查询以外全部拒绝，不是「用默认策略继续」。
「文件被删」也走这条路，否则删掉策略文件就等于放开所有开发工具。

### 3.3 模式差异

| 模式 | 未匹配时 | argv 白名单 | 传统 shell |
|---|---|---|---|
| `autonomy`（默认） | confirm | 生效 | confirm |
| `balanced` | confirm | 生效，且 cwd 必须在 `workspace_roots` 内 | confirm |
| `strict` | deny | 仅在显式规则下 | deny |
| `disabled` | deny | 不生效，连 allow 规则也不生效 | deny |

`disabled` 下只读查询（`query_system_info`、`query_service`、`read_state_file`）仍然可用，
便于自查。

## 4. 默认自动执行的操作

`mode=autonomy` 的默认策略放行以下 argv 程序（**不需要确认**）：

**开发工具链**
`git` `cargo` `rustc` `rustup` `rustfmt` `clippy-driver` `node`* `npm` `pnpm` `yarn` `npx`
`python`* `python3`* `py`* `pip` `go` `dotnet` `java` `javac` `mvn` `gradle`
`cmake` `ninja` `make` `msbuild` `cl` `link` `clang` `clang++` `gcc` `g++` `ld`
`objdump` `nm` `strings` `readelf` `r2` `rabin2` `7z` `tar` `ffmpeg` `magick`

`*` 表示带 `arg_forbid`：`node -e/--eval/-p/--print`、`python -c`、`py -c` 被排除
（这些等于内联任意代码，不属「跑脚本/跑构建」的常规形态）。

**包管理器**（任务书要求的「常用软件安装自动化」）
`winget` `choco` `scoop`

**只读系统信息**
`systeminfo` `ipconfig` `whoami` `hostname` `tasklist` `netstat` `driverquery`
`pnputil` `powercfg` `where`

**结构化只读操作**
`query_system_info`、`query_service`、`read_state_file`（文件白名单只有 `policy.toml`）

默认需要确认：`sc` `reg` `netsh` `schtasks` `takeown` `icacls` `bcdedit` `diskpart`、
未列入 `approved_services` 的 `restart_service`、以及所有传统 shell。

默认**直接拒绝**（内置，不可配置）：

| 类别 | 例子 | 规则 ID |
|---|---|---|
| 间接执行宿主 | `cmd` `powershell` `pwsh` `wscript` `cscript` `mshta` `rundll32` `regsvr32` `wsl` `bash` `sh` | `builtin:shell-host` |
| 下载器 | `certutil`（只放行 `-hashfile/-dump/-verify/-store`）`bitsadmin` `curl` `wget` | `builtin:downloader` |
| 磁盘/引导不可逆 | `format` `diskpart` `bcdedit` `vssadmin delete` `wbadmin delete` `cipher /w` | `builtin:destructive` |
| 关闭安全控制 | `wevtutil cl` `auditpol /clear` `Set-MpPreference` `netsh advfirewall set` | `builtin:destructive` |
| 持久化 | `sc create/delete/config` `schtasks /create` `reg add …\Run` | `builtin:destructive` |
| 提权账户 | `net user … /add` `net localgroup administrators … /add` | `builtin:destructive` |
| 凭据转储 | `procdump` `mimikatz` `pwdump` | `builtin:destructive` |
| 改 AI-Root 自身 | 任何参数指向 `%ProgramData%\AI-Root` | `builtin:self-protect` |
| 管道内更新自身 | `op=update_self` | `builtin:update-gated` |

## 5. 如何添加自动化规则

规则写在 `policy.toml` 的 `[[rule]]` 段里，或者拆到 `rules.d\*.toml`。
后者只需写 rule 表，不用重复顶层配置，推荐日常维护用这个。

编辑方式（文件 ACL 只允许管理员写）：

```powershell
Start-Process notepad "C:\ProgramData\AI-Root\rules.d\90-local.toml" -Verb RunAs
AI-Root config check
```

改完不用重启服务，下次请求就按新策略判定；配置有错会在 `config check` 里报出来。

### 5.1 放行一个新工具

想让 `ruff` 自动执行，新建 `rules.d\90-local.toml`：

```toml
[[rule]]
id = "allow-ruff"
decision = "allow"
op = "run_argv"
program = "ruff"
note = "Python linter"
```

### 5.2 只允许某个程序的特定子命令

```toml
[[rule]]
id = "allow-git-status-only"
decision = "allow"
op = "run_argv"
program = "git"
arg_prefix = ["status"]
note = "只允许 git status，不含 push/pull"
```

`arg_prefix` 是逐项相等的，`git status` 匹配，`git status --short` 也匹配，
但 `git push` 不匹配，会退回默认判定。

### 5.3 只在项目目录内允许构建

```toml
[[rule]]
id = "allow-cargo-in-workspace"
decision = "allow"
op = "run_argv"
program = "cargo"
cwd_roots = ["D:\\project", "C:\\Users\\example\\source"]
```

`cwd_roots` 是硬约束。请求没带 `--cwd`，或者带的目录不在根内，规则都不匹配。
路径按目录边界比较，`C:\project-evil` 不会被 `C:\project` 误判成子目录。

### 5.4 放行几个服务的重启

这个不用写规则，改 `policy.toml` 的顶层数组即可：

```toml
approved_services = ["Spooler", "wuauserv", "Dnscache"]
```

之后 `AI-Root op restart_service --target Spooler` 直接执行。

### 5.5 临时收紧

把 `mode` 改成 `"strict"`，未显式允许的一律拒绝，只读查询仍可用。
改回 `"autonomy"` 即恢复。

## 6. 确认机制

### 6.1 确认通道不用弹窗的原因

服务以 LocalSystem 运行在 session 0，没有交互桌面，弹不出窗口。
如果硬要做服务端弹窗，就得在用户会话里常驻一个接收端，那等于新增一块攻击面。
所以确认通道做成「文件 + 管理员命令」的形式。

### 6.2 完整流程

```text
① AI 执行一条需要确认的命令
   AI-Root exec winget install SomePackage
   → 退出码 3，输出：
     需要人工确认：
       请求 ID : 52f2d3f6524111b4
       操作    : run_argv
       参数    : argv=[winget install SomePackage]
       风险    : 结构化执行 `winget`：程序与参数已固定……
       有效期  : 300s
     管理员批准：AI-Root approve 52f2d3f6524111b4

② 用户（管理员终端）
   AI-Root approve 52f2d3f6524111b4

③ AI 重新执行**同一条命令**
   → 这次匹配到批准，正常执行；批准被一次性消费
```

其它命令：

```powershell
AI-Root pending            # 列出所有待确认请求（含风险说明）
AI-Root deny <id>          # 拒绝
```

### 6.3 安全属性

| 属性 | 实现 |
|---|---|
| 不可伪造 | `pending\` 目录继承数据目录 ACL，普通用户（含 Agent）**无法写入** `.approved` |
| 与参数绑定 | 批准内容 = `sha256(op \| 完整参数摘要)`；参数改一个字符就是另一个哈希 |
| 一次性 | 批准被消费即删除 |
| 过期即废 | 请求与批准都带 TTL，`approve` 拒绝过期请求 |
| 不接受客户端声明 | 协议 `deny_unknown_fields`，发 `confirmed: true` 会**解析失败** |
| 不占死连接 | 首次请求立即返回，不等确认；批准后重放，不会把并发槽占满 5 分钟 |

## 7. 更新与回滚

### 7.1 更新（`AI-Root update`）

v1.1 起，`update` 有三道门控，**任一不满足即拒绝**：

1. **Authenticode 嵌入签名**通过 `WinVerifyTrust`（catalog 签名不算）；
2. 签名者证书 SHA-256 命中 `trusted_publishers`；
3. 目标路径 = SCM 实际 `ImagePath`，且必须位于 `%ProgramData%\AI-Root`（受 ACL 保护）。

另加：架构必须与当前进程一致、拒绝版本降级、复制后二次比对 SHA-256、
启动 20s 内未 Running 则**自动回滚**到 `.old`。

### 7.2 建立信任根（一次性，需管理员）

```powershell
# 1) 查看发布包签名（不发管理员也行，只读）
AI-Root signature .\AI-Root-new.exe

# 2) 确认「签名者」与「证书 SHA-256」确实是你的发布证书后，加入信任根
AI-Root trust-publisher .\AI-Root-new.exe

# 3) 之后即可自主更新（非提权）
AI-Root update D:\path\to\AI-Root-new.exe
```

未配置 `trusted_publishers` 时，`update` **一律拒绝**（安全失败），
并提示先执行 `trust-publisher`。

这里只接受嵌入签名。Windows 系统目录里的程序大多是 catalog 签名，签名放在 `.cat`
文件里而不在 PE 内，`WinVerifyTrust` 的 `GENERIC_VERIFY_V2` 默认看不到。
这个限制比 catalog 更严格，代价是发布流程要配合
`signtool sign /fd sha256 /a AI-Root.exe`。

### 7.3 回滚

- **自动**：新版本启动失败/未在 20s 内 Running → 停止 → 恢复 `.old` → 重启旧版本。
- **手动**（离线）：
  ```powershell
  sc stop AI-Root
  Move-Item C:\ProgramData\AI-Root\AI-Root.exe.old C:\ProgramData\AI-Root\AI-Root.exe -Force
  sc start AI-Root
  ```
  注意：`.old` 只在替换后、健康检查通过前存在；成功更新后会删除。
- **版本降级被拒绝**时同样适用上面的手动流程。

## 8. 已知限制

| 限制 | 说明 |
|---|---|
| 令牌仍是全权凭据 | 令牌本身不分级；分级靠策略层。令牌泄漏 = 可发起任意请求（但受策略约束） |
| 解释器 = 代码执行 | 允许 `python`/`cargo`/`node` 即等于允许任意代码（见 §2 的取舍说明） |
| 不检查证书吊销 | `WTD_REVOCATION_CHECK_NONE`：服务可能在无网环境启动，联网检查会长时间挂起。信任根是固定指纹，风险可控 |
| 不验证 catalog 签名 | 只接受嵌入签名（比默认更严格） |
| `pending\` 无自动清理 | 过期请求在下次同参数请求时被覆盖；可用 `AI-Root pending` 查看，管理员可手工删除 |
| 传统 shell 只能整条确认 | 字符串无法结构化匹配；能用 `exec` 就别用 `run` |
| 内置保护是「模式匹配」 | shell 模式下 `f^ormat` 这类 cmd 转义改写能绕过字符串检查，所以 shell 必须确认，而且确认时用户能看到完整命令 |
| 服务可被安装用户停止 | `install` 仍授予 `GRGX`（含 STOP/START），用于零 UAC 更新。现在更新有签名门控，DoS 风险保留（见审计 V-14） |
| 确认需要管理员在场 | 设计如此：确认真实性依赖「只有管理员能写 pending 目录」 |

## 9. 排障

```powershell
AI-Root status                  # 服务状态 / 启用标志 / 管道 / 令牌
AI-Root policy                  # 当前策略与自动允许范围
AI-Root tail                    # 实时事件流
AI-Root tail --type policy_decision   # 只看授权判定
AI-Root tail --type confirm_consumed  # 只看确认被消费
```

审计事件类型：

| type | 含义 |
|---|---|
| `policy_decision` | 每次请求的判定（含 deny 与降级状态） |
| `exec_done` / `command_audit` | 执行结果（含 decision / rule_id / confirmed） |
| `confirm_consumed` | 某份批准被使用 |
| `update_rejected` / `update_rollback` / `update_done` | 更新流程各阶段 |
| `acl_setup_failed` | 启动时 ACL 设置/校验失败（服务会拒绝启动） |
| `temp_cleanup_failed` | 临时脚本清理失败（文件路径会记录） |
| `taskkill_failed` | 超时杀进程树失败（已降级为 kill 直接子进程） |

日志位置：`%ProgramData%\AI-Root\events.jsonl`（实时流，2MB 轮转）、`exec.log`（审计）。
日志中的命令参数经 `redact()` 脱敏（`--password=`、`-p`、`API_KEY=` 等）。
