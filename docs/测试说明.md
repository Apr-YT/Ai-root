## 3. 测试策略（三条硬性原则）

### 3.1 测试必须调用真实被测代码

帧测试**真实调用** `write_frame` 并校验落盘字节，
而非在测试内重抄一遍编码逻辑。

早期曾在测试里重抄 `write_frame` 的编码逻辑，那种写法实现改错了测试也照样通过，
不能算被测到。

### 3.2 ★ 无法在测试环境复现的前提，要么抽纯函数，要么就不算被测到

首版测试直接断言 `granted_user_sid() != S-1-5-18`，
变异验证实测漏检，因为测试进程永远不是 SYSTEM，`whoami` 在测试里返回的本来就是真实用户。

抽出纯函数 `select_grant_sid(persisted, current)` 后，可注入 `(SYSTEM, SYSTEM)` 组合断言 `None`，
变异随即 FAILED。

凡是依赖当前进程身份、权限或环境的逻辑，都要把决策部分抽成纯函数才可测。

### 3.3 阈值类断言硬编码期望值

不要引用常量，引用的话「改常量」的变异会漏检，测试会跟着一起变。

已有 `auth_window_and_lock_durations_match_contract` 锁定 **30s / 120s**。

这些数值是对外承诺的**行为契约**（见 [README §安全模型](../README.md#安全模型)），
变更应是有意识的决策。

### 3.4 端到端测试的集成方式

`handle_client` 5 个测试真实驱动「读请求帧 → 序列化校验 → 鉴权 → 执行 → 回写响应」全链路：
主线程当客户端、工作线程跑**真实** `handle_client`，**不 mock 任何环节**。

覆盖：有效令牌正常执行、错误令牌拒绝且不执行命令、禁用开关生效、
退出码透传（`cmd /c exit 7` → 7）、非法请求在执行前被拦。

**三个环境隔离要点**（缺一不可）：

1. `AIROOT_DATA_DIR` 指向临时目录，否则 `cached_token` 和 `is_enabled` 会读到生产值；
2. `AUTH_THROTTLE` / `SID_FAILS` / `ACTIVE_CONNS` 是**进程级 static**
   → 用全局锁 `E2E_LOCK` **串行化**本组用例，否则一个用例的失败计数污染另一个的鉴权结果；
3. `LOGGER`（`OnceLock`）首次写日志即绑定 `data_dir()` 且不再改
   → 本组必须共享同一 `AIROOT_DATA_DIR`。

### 3.5 集成测试用真实 IO

- **真实命名管道**：`read_frame_timeout` 通过 `make_pipe_pair()` 在进程内自建
  `CreateNamedPipeW` + `CreateFileW` 管道对（管道名含 `pid` + 测试标签，保证并行安全），
  **不 mock 任何 IO**。因此它真实覆盖了 `PeekNamedPipe` 轮询、分段超时预算、
  `FRAME_MAX_SIZE` 长度前缀校验这几条最容易出安全 bug 的路径。
- **真实 `icacls`**：ACL 测试先构造「父目录授予可继承 Users 写权限」这一危险前提
  **并断言前提成立**，再调真实 `set_dir_acl`，最后断言结果。
  前提不成立时测试主动失败（避免「前提没了还假装通过」）。

`HANDLE` 不是 `Send`，不能跨线程返回，必须在线程内包成 `File`。

## 4. 变异验证记录

要验证测试是否有效，唯一办法是变异测试：改坏实现，看测试会不会 FAILED。

| # | 注入的变异 | 结果 | 备注 |
|---|---|---|---|
| 1 | `to_le_bytes` → `be` | FAILED | 帧长度前缀字节序 |
| 2 | `ct_eq` → 仅比首字节 | FAILED | 恒定时间比较 |
| 3 | 熔断阈值 20 → 21 | FAILED | 硬编码期望值的意义 |
| 4 | 移除 `FRAME_MAX_SIZE` 校验 | FAILED | 仅 `read_frame_rejects_oversized_length_prefix` 失败 |
| 5 | 移除头部空闲超时检查 | FAILED | `read_frame_times_out_when_no_data_sent` 直接挂死，被 timeout 杀掉，说明它守的是线程泄漏型 DoS |
| 6 | 把 `/inheritance:r` 改回 `/inheritance:e` | FAILED | 两个 ACL 测试均失败 |
| 7 | 去掉 SID 的 `*` 前缀 | 首次未捕获 | 补了「当前用户保留只读 ACE」断言之后才捕获 |
| 8 | 只断言 `granted_user_sid() != S-1-5-18` | 实测漏检 | 抽出纯函数 `select_grant_sid()` 后捕获 |
| 9 | 移除 `current` 分支的 `sid != LOCAL_SYSTEM_SID` 守卫 | FAILED | |
| 10 | 移除 `persisted` 分支的同一守卫 | FAILED | |
| 11 | 取消鉴权（`ct_eq` 恒真） | FAILED | 仅 `e2e_..._rejects_wrong_token` 失败 |
| 12 | 去掉 `is_enabled()` 检查 | FAILED | 仅 `e2e_..._respects_disabled_flag` 失败 |
| 13 | 退出码硬编码为 0 | FAILED | 仅 `e2e_..._passes_through_exit_code` 失败 |

变异 11 到 13 都是精确命中，每次只有对应的那一个测试 FAILED，说明端到端测试之间没有交叉污染。

### 关键教训

- 变异 7 和 8 属于漏检，两者都不是读代码读出来的，是跑变异跑出来的。
  这正说明变异测试的价值：不跑一次，就不知道断言其实没覆盖到。
- 变异 5 让测试挂死而不是失败。对超时类逻辑，测试挂起本身就是有效信号。

### 操作注意

改坏源码验证测试时，**务必先备份**：

```bash
cp src/x.rs /tmp/x.rs.bak
# ... 改坏、跑测试、观察 FAILED ...
cp /tmp/x.rs.bak src/x.rs
cargo test   # 确认恢复后全绿
```

## 5. 已知缺口

按优先级从高到低：

| 缺口 | 难点 |
|---|---|

## 6. v1.1 新增测试的设计说明（2026-10-21）

### 6.1 为什么策略测试要断言「内置保护优先于 allow 规则」

这是本次改造最重要的结构性保证。测试 `builtin_denies_shell_hosts_even_if_rule_allows`
会在策略表**最前面插入**一条 `allow cmd` 规则，然后断言 `cmd /c` 仍被拒。
若有人把实现改成「先扫 allow 再扫 builtin」，该测试立即 FAILED。

### 6.2 为什么确认流程测试要跑「三次」

`e2e_confirm_then_replay_executes` 断言：

1. 第 1 次 → `decision=confirm` + 有 `confirmation_id` + **stdout 无输出**（未执行）；
2. 批准后第 2 次 → `ok=true` + 输出出现；
3. 第 3 次 → 又回到 `confirm`（批准已被消费）。

只测第 2 步会漏掉「批准可被无限复用」这个失效模式。

### 6.3 为什么签名测试要区分嵌入签名与 catalog 签名

Windows 系统目录里的 exe 绝大多数是 **catalog 签名**（签名在 `.cat` 里），
`WinVerifyTrust` 的 `GENERIC_VERIFY_V2` 看不到它。实测 `notepad.exe` 返回
`0x800B0100 (TRUST_E_NOSIGNATURE)`，而 Python 的 `python.exe` 能通过并给出指纹。

因此测试用两个样本分别钉住两种行为：
- `catalog_signed_system_binary_is_not_accepted`：确认我们**只接受嵌入签名**；
- `signed_binary_exposes_thumbprint`：确认嵌入签名能提取指纹且白名单比对生效。

找不到嵌入签名样本时测试**打印 skip 并返回**，不谎报通过。

### 6.4 为什么 ACL 测试要人为「改坏」

`verify_dir_acl_*` 三个测试都先构造失败前提（授 Everyone 写 / 父目录继承 Users 写 /
目录不存在），再断言校验器能检出。只测「正确配置通过」无法证明校验器在工作
（一个恒返回 `Ok(())` 的实现也能通过）。

### 6.5 测试隔离修正

改造前跑 `cargo test` 会在真实 `%ProgramData%\AI-Root` 下创建目录并写入日志
（`logger()` 首次绑定 `data_dir()`）。v1.1 把测试构建的日志目录固定到
`%TEMP%\airoot-test-logs`，并已验证「跑完全量测试后真实目录不会被创建」。

### 6.6 仍未验证的部分（明确记录，不声称通过）

| 项 | 原因 |
